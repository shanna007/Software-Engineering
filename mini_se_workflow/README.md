# 基于 Mini SE 的多 Agent Workflow 系统设计与实现

## 1. 项目简介与项目目标

### 1.1 项目简介

本项目基于软件工程课程任务，设计并实现了一个基于大语言模型的多 Agent Workflow 系统。系统模拟简化的软件开发流程，将软件开发任务拆分为需求分析、系统设计、代码生成和自动化测试四个阶段，通过多个具有独立职责的 Agent 协同完成从用户需求到代码实现及测试验证的完整过程。

系统采用顺序执行的 Workflow 编排方式，由统一的工作流控制器负责调度各 Agent。各 Agent 通过共享的全局状态对象传递任务信息和阶段产物，并记录执行日志与运行状态。需求分析 Agent 和系统设计 Agent 使用结构化 JSON 输出，降低不同阶段之间的信息歧义；代码生成 Agent 根据设计结果生成 Python 代码；自动化测试 Agent 生成并执行单元测试，形成测试报告。

本项目采用模块化设计，Agent 通过统一的基类和接口进行扩展，便于后续增加代码审查、文档生成和缺陷修复等功能。

### 1.2 项目目标

本项目的主要目标如下：

1. **实现完整的工作流：** 建立从需求分析、系统设计、代码生成到自动化测试的顺序执行流程。
2. **实现多 Agent 协作：** 将不同软件工程任务分配给独立 Agent，明确职责边界。
3. **实现统一状态管理：** 通过共享状态对象保存用户需求、阶段输出、测试报告、执行日志和工作流状态。
4. **实现标准化信息传递：** 使用结构化 JSON 输出约束需求与设计阶段的结果格式，提高 Agent 间的信息传递一致性。
5. **实现异常处理与执行记录：** 记录各阶段的执行情况，在发生异常时更新工作流状态并终止后续执行。
6. **提高系统可扩展性：** 通过统一 Agent 接口和独立模块设计，支持新增 Agent 或调整工作流执行顺序。

## 2. 整体架构设计

### 2.1 系统架构

系统采用分层、模块化的架构，主要由 Workflow 编排层、Agent 执行层、共享状态层、模型调用层和测试执行层组成。

| 模块            | 主要职责                                                     |
| --------------- | ------------------------------------------------------------ |
| Workflow 编排层 | 按预定顺序调度 Agent，控制流程执行，处理异常和最终状态       |
| Agent 执行层    | 实现需求分析、系统设计、代码生成和自动化测试等独立任务       |
| 共享状态层      | 保存用户需求、阶段产物、测试报告、日志和工作流状态           |
| 模型调用层      | 封装大语言模型 API 调用，支持文本生成和结构化 JSON 生成      |
| 测试执行层      | 对生成的 Python 代码进行基础静态检查，执行单元测试并汇总结果 |
| 文件输出层      | 将需求分析、设计结果、生成代码、测试报告和执行报告保存到本地 |

各模块之间通过明确的接口协作，避免将所有逻辑集中在单个程序中，从而降低模块之间的耦合程度。

### 2.2 Workflow 编排方案

本项目采用**中心化、顺序执行的 Workflow 编排方案**。Workflow 是整个系统的控制中心，负责决定 Agent 的执行顺序，并在每个阶段结束后检查执行结果。

系统的执行顺序如下：

1. 用户输入软件开发需求。
2. 需求 Agent 对自然语言需求进行分析，输出结构化需求说明。
3. 设计 Agent 根据需求说明生成系统设计方案。
4. 编码 Agent 根据需求和设计结果生成 Python 代码。
5. 测试 Agent 生成单元测试并执行测试，输出测试报告。
6. Workflow 汇总执行情况，保存阶段产物和最终执行报告。

每个 Agent 仅负责自身任务，不直接控制整个工作流。各阶段按照预设顺序执行；如果某个阶段发生未处理的异常，Workflow 将记录错误并将整体状态标记为失败，避免后续阶段在缺少必要输入的情况下继续执行。

### 2.3 Agent 通信方式

本项目采用**基于共享状态对象的通信方式**，而非 Agent 之间直接互相调用。

所有 Agent 均访问统一的 `WorkflowState` 对象。当前阶段的 Agent 从状态对象中读取前序阶段的结果，完成任务后再将输出写回状态对象，供后续 Agent 使用。

主要传递的数据包括：

- `user_request`：用户提交的原始需求。
- `requirement`：需求 Agent 生成的结构化需求说明。
- `design`：设计 Agent 生成的系统设计方案。
- `generated_code`：编码 Agent 生成的 Python 代码。
- `test_report`：测试 Agent 生成的测试结果。
- `logs`：记录各 Agent 的执行过程和异常信息。
- `status`：记录 Workflow 的整体执行状态。

这种方式能够减少 Agent 之间的直接依赖，使各 Agent 通过统一的数据接口交换信息，便于调试、维护和扩展。

此外，需求和设计阶段采用 JSON Schema 约束结构化输出，明确字段名称、数据类型和必需字段，降低自然语言输出格式不统一带来的解析问题。

### 2.4 状态管理方案

系统通过统一的 `WorkflowState` 类管理整个工作流的运行数据。状态对象贯穿工作流的执行过程，负责保存输入、阶段产物、执行日志和运行状态。

状态管理主要包含以下内容：

1. **输入管理：** 保存用户原始需求，确保各 Agent 围绕同一任务开展工作。
2. **阶段结果管理：** 保存需求、设计、代码和测试报告，支持后续阶段读取。
3. **日志管理：** 记录 Agent 开始执行、执行成功和发生异常等事件。
4. **状态管理：** 通过状态字段反映工作流的整体执行情况，例如运行中、成功或失败。
5. **结果持久化：** 将关键阶段的输出保存到本地文件，方便检查和复现。

统一状态对象有助于保持工作流中数据的一致性，也便于在后续版本中加入任务重试、执行历史、断点恢复和多分支流程等能力。

## 3. Mermaid 流程图

以下流程图展示了系统的主要执行过程。各 Agent 按照预定顺序执行，测试完成后输出执行报告；若任一阶段出现异常，则记录错误并结束当前工作流。

```
flowchart TD
    A([开始]) --> B[用户输入开发需求]
    B --> C[初始化 WorkflowState]
    C --> D[需求 Agent]
    D --> E{需求分析成功?}
    E -- 是 --> F[设计 Agent]
    E -- 否 --> X[记录异常并标记失败]
    F --> G{系统设计成功?}
    G -- 是 --> H[编码 Agent]
    G -- 否 --> X
    H --> I{代码生成成功?}
    I -- 是 --> J[测试 Agent]
    I -- 否 --> X
    J --> K[生成并执行单元测试]
    K --> L[汇总测试报告]
    L --> M[保存阶段产物与执行日志]

    N --> O([结束])
    X --> P[保存错误信息与执行报告]
    P --> O
```

该流程图体现了顺序编排、阶段间数据依赖、异常处理和统一结果输出等核心机制。

## 4. Agent 职责拆分

系统将软件开发流程拆分为四个主要 Agent。各 Agent 具有明确的职责边界，并通过共享状态对象完成协作。

### 4.1 需求分析 Agent（RequirementAgent）

**主要职责：** 将用户输入的自然语言需求转换为结构化的软件需求说明。

主要工作包括：

- 理解用户的开发目标和功能要求。
- 提取核心功能、输入输出和约束条件。
- 梳理主要功能点及其验收标准。
- 通过 JSON Schema 约束输出格式，确保结果符合预定的数据结构。
- 将结构化需求写入共享状态对象。

**输入：** 用户原始需求。

**输出：** 结构化需求说明，包括项目目标、功能需求、输入输出和验收标准等信息。

该 Agent 为后续设计和编码提供统一的需求依据，减少需求理解不一致造成的问题。

### 4.2 系统设计 Agent（DesignAgent）

**主要职责：** 根据需求分析结果制定系统设计方案。

主要工作包括：

- 分析需求之间的关系和依赖。
- 划分系统模块，明确各模块的职责。
- 设计主要接口、数据结构和调用关系。
- 根据需求确定必要的实现步骤。
- 通过 JSON Schema 约束设计输出，保证后续编码 Agent 能够稳定读取。
- 将设计结果写入共享状态对象。

**输入：** 结构化需求说明。

**输出：** 结构化系统设计方案，包括模块划分、接口设计、数据结构和实现计划等信息。

该 Agent 将抽象需求转换为可执行的设计方案，为代码生成阶段提供指导。

### 4.3 代码生成 Agent（CodeAgent）

**主要职责：** 根据需求和系统设计生成可执行的 Python 代码。

主要工作包括：

- 读取需求说明和系统设计方案。
- 根据设计结果生成 Python 源代码。
- 对生成的代码执行基础语法检查。
- 在语法检查未通过时报告错误，避免将明显存在语法问题的代码直接交给后续阶段。
- 将生成代码写入共享状态对象，并由主程序保存到本地文件。

**输入：** 结构化需求说明和系统设计方案。

**输出：** Python 源代码。

代码生成 Agent 将前序阶段的分析结果转化为实际程序，是从设计到实现的关键环节。需要注意，语法检查通过并不代表代码逻辑正确，仍需通过后续测试进行验证。

### 4.4 自动化测试 Agent（TestAgent）

**主要职责：** 为生成的代码生成并执行单元测试，检查基本功能是否符合预期。

主要工作包括：

- 根据需求、设计和生成代码分析测试目标。
- 生成 Python `unittest` 测试用例。
- 调用测试执行模块运行测试。
- 汇总测试通过数、失败数、错误信息和执行状态。
- 将测试结果写入共享状态对象，并生成测试报告。

**输入：** 需求说明、设计方案和生成的 Python 代码。

**输出：** 单元测试代码和测试报告。

测试 Agent 补充了代码生成后的验证环节，使系统不仅能够生成代码，还能对代码进行初步质量检查。测试结果用于判断程序是否满足已覆盖的测试条件，但不能保证程序不存在所有缺陷。

## 5. 可扩展性设计

### 5.1 统一 Agent 基类

系统通过 `AgentBase` 为各 Agent 提供统一的基础接口。新增 Agent 时，可以继承该基类，并实现自身的执行逻辑。

这种设计使 Workflow 不需要了解每个 Agent 的内部实现细节，只需要按照统一接口调用 Agent 即可。

新增 Agent 的基本步骤如下：

1. 在 `agents/` 目录下创建新的 Agent 模块。
2. 定义新 Agent 类并继承 `AgentBase`。
3. 实现对应的任务处理逻辑。
4. 从共享状态对象中读取所需输入。
5. 将执行结果写入共享状态对象。
6. 在 Workflow 中注册该 Agent，并确定其执行位置。
7. 更新相关测试和项目文档。

例如，可以新增代码审查 Agent：

```
class ReviewAgent(AgentBase):
    def run(self, state):
        # 读取生成代码并进行代码审查
        # 将审查结果写入共享状态
        pass
```

以上代码仅用于展示扩展方式，具体方法签名应与项目中 `AgentBase` 的实际接口保持一致。

### 5.2 新增 Agent 的示例

在现有工作流中，可以增加一个代码审查 Agent，对生成代码进行规范性和潜在问题检查。

新增后的执行顺序可以调整为：

需求分析 Agent → 设计 Agent → 编码 Agent → 代码审查 Agent → 测试 Agent。

代码审查 Agent 可以重点检查：

- 代码结构和命名规范。
- 是否存在明显的逻辑问题。
- 是否符合设计方案。
- 是否存在不必要的重复代码。
- 是否存在潜在的异常处理问题。

审查结果可以写入共享状态对象，并作为测试阶段的补充参考。若需要实现审查不通过后自动返回编码阶段，则需要进一步增加条件分支和有限次数的重试控制。

### 5.3 修改 Workflow 流程

当前系统采用顺序执行方式，流程控制集中在 `Workflow` 类中。因此，修改执行顺序通常只需要调整 Agent 的注册或调用顺序。

例如，若希望在代码生成后先进行审查，再执行测试，可以将 Workflow 调整为：

```
def run(self, state):
    self.requirement_agent.run(state)
    self.design_agent.run(state)
    self.code_agent.run(state)
    self.review_agent.run(state)
    self.test_agent.run(state)
    return state
```

以上为流程调整示例，实际实现应沿用项目中已有的异常处理、日志记录和状态更新逻辑，避免绕过统一的调度机制。

如果未来需要支持更复杂的流程，可以进一步扩展：

- **条件分支：** 根据需求类型或执行结果选择不同的 Agent。
- **失败重试：** 在指定次数内重试失败的任务。
- **反馈闭环：** 测试失败后将测试报告反馈给编码 Agent，尝试修复代码。
- **并行执行：** 对相互独立的任务并行调度。
- **人工审核：** 在代码执行或最终交付前增加人工确认环节。

上述能力属于后续扩展方向，不代表当前版本已经全部实现。

## 6. 运行说明与测试案例

### 6.1 环境要求

- Python 3.10 或更高版本。
- 可用的大语言模型 API。
- 能够访问所配置模型服务的网络环境。
- 已安装项目所需的 Python 依赖。

项目通过环境变量管理 API 密钥和模型配置，避免将敏感信息直接写入源代码。

### 6.2 安装步骤

首先，进入项目根目录并安装依赖：

```
python -m pip install -r requirements.txt
```

然后复制环境配置模板：

```
# Linux / macOS
cp .env.example .env
```

Windows 命令提示符下可以使用：

```
copy .env.example .env
```

打开 `.env` 文件，根据实际使用的模型服务配置：

```
OPENAI_API_KEY=your_api_key_here
OPENAI_MODEL=your_supported_model_name
```

其中，`OPENAI_API_KEY` 应填写有效的 API 密钥，`OPENAI_MODEL` 应填写当前服务支持的模型名称。所选模型还需要支持项目所使用的 Responses API 和 JSON Schema 结构化输出能力。

**注意：** 不要将包含真实 API 密钥的 `.env` 文件提交到公开代码仓库。

### 6.3 启动程序

在项目根目录执行：

```
python main.py
```

启动后，根据终端提示输入软件开发需求。系统将依次执行需求分析、系统设计、代码生成和自动化测试，并在执行结束后输出结果文件。

### 6.4 输出文件说明

程序运行后，主要输出文件位于 `outputs/` 目录下。

| 文件                    | 说明                               |
| ----------------------- | ---------------------------------- |
| `requirement.json`      | 需求 Agent 输出的结构化需求说明    |
| `design.json`           | 设计 Agent 输出的系统设计方案      |
| `generated_code.py`     | 编码 Agent 生成的 Python 代码      |
| `test_generated.py`     | 测试 Agent 生成的单元测试代码      |
| `test_report.json`      | 自动化测试结果及相关信息           |
| `execution_report.json` | 工作流执行状态、日志和执行结果摘要 |

具体输出文件是否生成，取决于工作流执行到的阶段以及该阶段是否成功完成。

### 6.5 测试案例一：学生成绩管理系统

**测试目的：** 验证系统能否根据自然语言需求完成需求分析、系统设计、代码生成和自动化测试。

**输入需求示例：**

> 开发一个简单的学生成绩管理系统，支持添加学生、录入多门课程成绩、计算学生平均分、按照平均分排序、根据学生姓名查询成绩，并支持保存和加载数据。

**预期执行过程：**

1. 需求 Agent 提取学生管理、成绩录入、平均分计算、排序、查询和数据持久化等功能。
2. 设计 Agent 规划学生数据结构、成绩处理方法和文件读写接口。
3. 编码 Agent 根据设计方案生成 Python 实现。
4. 测试 Agent 生成并执行相应的单元测试。
5. Workflow 保存阶段产物和测试报告。

**建议检查的测试点：**

| 测试点         | 验证内容                               |
| -------------- | -------------------------------------- |
| 添加学生       | 能否正确保存学生信息                   |
| 录入成绩       | 能否正确记录多门课程成绩               |
| 计算平均分     | 平均分计算结果是否正确                 |
| 排序           | 学生是否按照平均分正确排序             |
| 姓名查询       | 是否能够查询指定学生的成绩             |
| 数据保存与加载 | 保存后重新加载的数据是否符合预期       |
| 异常输入       | 对不存在的学生或无效成绩是否有合理处理 |

该案例覆盖了常见的数据处理和文件操作任务，适合作为课程项目的基本功能验证案例。

### 6.6 测试案例二：异常处理验证

**测试目的：** 验证工作流在 Agent 执行失败时能否正确记录异常并更新状态。

**测试方法：**

可以通过模拟模型调用失败、结构化输出解析失败或代码生成语法错误等方式触发异常。

**预期结果：**

1. 系统能够捕获并记录相关错误信息。
2. Workflow 将整体状态更新为失败。
3. 后续依赖该阶段输出的 Agent 不再继续执行。
4. 系统尽可能保存已有阶段产物和执行报告。
5. 用户能够根据日志定位失败阶段。

此案例用于验证系统的异常处理能力，而不是检验生成代码的功能正确性。

### 6.7 测试案例三：结构化输出验证

**测试目的：** 验证需求 Agent 和设计 Agent 的输出是否符合预定的数据结构。

**测试方法：**

分别检查 `requirement.json` 和 `design.json`，确认必需字段是否存在、字段类型是否正确，以及输出是否符合对应的 JSON Schema。

**预期结果：**

- 输出可以被正确解析为 JSON。
- 必需字段完整。
- 字段类型符合定义。
- 不包含 Schema 禁止的额外字段。
- 结构化结果能够被后续 Agent 正确读取。

如果模型调用失败或输出不符合预期，应记录相应错误，并按照系统当前的异常处理逻辑终止后续依赖阶段。

### 6.8 测试执行的安全说明

测试执行模块会对生成的 Python 代码进行基础静态检查，并通过独立子进程和执行超时限制运行单元测试。

这些措施有助于减少部分风险，但 **AST 静态检查和子进程隔离并不等同于强安全沙箱**，不能完全阻止恶意代码访问文件、网络或系统资源。因此，不应直接运行未经审查的模型生成代码。若需要在真实业务环境中使用，应进一步采用容器、虚拟机或其他具有明确资源和权限限制的隔离机制。

此外，单元测试通过只能说明已覆盖的测试用例符合预期，不能证明程序完全正确。
